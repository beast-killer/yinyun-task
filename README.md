# 积压工时 ≥60h 的工单，一次修复失败率是低负荷工单的 4.9 倍

> 数据：`repair_dispatches.csv`，1,107 行，去重后 1,054 单，覆盖 2026-08-31 ~ 2026-09-07。
> 结果已回传 1,005 单，总体失败率 **10.55%**（106/1005）。

## 1. 我的判断

### 我看到的三个事实

1. **手册同步是实时的，不是失效的。** 派工时 `manual_synced_at` 相对 `dispatch_time` 的滞后，中位数 **0.20 小时**，P95 0.99 小时，**最大值只有 1.17 小时**，没有任何一单超过 24 小时。题干假设的「方案信息失效」在这份数据里不存在。
2. **备件缺货只占 4.2% 的工单。** 缺货时失败率 19.0%，充足时 9.9%，方向对得上，但盘子太小（42 单），撑不起整体 10.55% 的失败率。
3. **积压工时把这批工单切成了三层。** `<40h` 失败率 3.8%，`40-60h` 8.1%，`≥60h` **18.7%**。

### 根问题

**失败的主因不是信息失效，是派工时段积压过高导致技师赶工。**

积压 ≥60h 的工单失败率 18.7%，是 <40h 工单（3.8%）的 **4.9 倍**。这个关系在 **5 个网点内部全部同向**（差值 +0.2 ~ +19.9pp），说明不是某个网点的局部现象，也不是网点混杂造成的假象。

### 我改过一次主意

我最初根据题干「方案或备件信息失效」，把重点放在 `manual_synced_at` 上，准备做「手册陈旧度 → 失败率」的分析。跑完分布才发现滞后最大只有 1.17 小时——这条线索直接关闭了。

**另一个必须处理的坑**：`dispatch_time` 带 `+08:00`，`manual_synced_at` 带 `Z`（UTC）。如果直接当本地时间相减，会凭空多出 8 小时，把「同步及时」误判成「滞后 8 小时」，整份分析的方向就反了。

### 我主动放弃的

没有做「故障类别 × 网点」的交叉分析。类别之间确实能看到失败率差异，但两层交叉后每格只剩 20-30 单，不足以支撑结论。**这是主动取舍，不是遗漏。**

## 2. 做了什么

- **分析单元**：一个 `ticket_id` 一行。原始 1,107 行中有 **53 行完全重复**（同票重复派工记录），已剔除，剩 1,054 单。
- **失败率分母**：只用 `is_resolved` 非空的行（1,005 单）。**49 单结果未回传，既不算成功也不算失败，直接剔除**——把它们当成功会低估失败率，当失败会高估。
- **核心口径**：`失败率 = is_resolved==0 的单数 / 结果已回传的单数`，按 `labor_hours` 分档统计。
- **方法**：分档对比 + 卡方检验 + Cramér's V（效应量）+ Spearman 单调性检验 + 网点分层复核。
  用效应量而不只看 p 值，是因为 1,005 单的样本量下 p 值几乎必然显著，看不出差异是否值得行动。

### 我遇到的歧义与我的处理

| 歧义点 | 我的判断 | 依据 |
|---|---|---|
| 53 行完全重复 | 剔除 | `ticket_id` 去重后正好 1,054 个，说明是同一张票被重复记录，不是两次独立派工 |
| 49 单结果未回传 | 从分母剔除，不填充 | 回传状态未知，填 0 或 1 都是编造；剔除后明确标注了剩余分母 |
| 两个时间列时区不一致 | 统一转 UTC 后再相减 | 一个带 `+08:00` 一个带 `Z`，不转换会差 8 小时 |
| 积压分档边界为什么是 40/60 | 看数据里的失败率台阶 | 20-40h 稳定在 3~3.4%，40-50h 跳到 8.7%，60-70h 再跳到 18.3%，台阶在 40 和 60 |

## 3. 怎么证明有用

| 结论 | 数字 | 由什么算出 |
|---|---|---|
| 手册滞后不构成问题 | 中位数 0.20h，最大 1.17h | `python repro.py --section 1` |
| 积压 ≥60h 失败率是低负荷的 4.9 倍 | 18.7% vs 3.8%（p=2.47e-08，V=0.187） | `python repro.py --section 2` |
| 该关系在 5/5 网点内部同向 | 差值 +0.2 ~ +19.9pp | 同上，分层复核表 |
| 备件缺货影响真实但面小 | 19.0% vs 9.9%，仅占 4.2% 工单 | `python repro.py --section 3` |

### 关键结论：「提前拦截重派」这门生意是亏的

题干给的两个价码必须拿来算账，否则「提前拦截」听起来天经地义：

- 拦截一单成本 **15h**，拦对一次省 **75h**
- **盈亏平衡：失败率必须 > 20% 才划算**
- 实际整体失败率 **10.55%**，高负荷组也只有 **18.7%**——**差一点点，但仍然不够**

| 场景 | 单量 | 净收益 |
|---|---|---|
| A. 拦截全部 ≥60h 工单 | 316 | **−1,227h**（比不拦更亏） |
| B. 不拦截，直接把积压压到 <40h 水平 | — | **+3,513h** |
| C. 只拦截「≥60h 且缺货」窄口 | 34 | +0.4h/单（能赚，但盘子太小） |

**所以正确的动作不是拦截重派，是降低积压。** 同样的 47 次失败可以被避免，但走调度的路不用付 15h/单的拦截成本。

### 一个反例，也是最有用的证据

**华东总站在高负荷下失败率只有 6.3%，和它低负荷时的 6.1% 几乎没差别**（其他四个网点的同项差值是 16.4~19.9pp）。

同样有 29.9%（63/211）的工单积压 ≥60h，它就是不掉。这说明**积压带来的失败不是宿命，是可管理的**——这是「降低积压」这个建议最硬的支撑：有现成的对照样本。

### 可行动的落点

调度团队现在只能凭感觉判断「今天忙不忙」。这个分析给出一个具体阈值：

> **对 `labor_hours ≥ 60` 的新派工单做分流（延后非紧急工单 / 调邻近网点支援），优先处理其中 `parts_available ≤ 2` 的。** 后者失败率 20.6%，是唯一过了盈亏平衡线的细分群。

观测指标：高负荷工单占比（当前 316/1005 = 31.4%）与高负荷组失败率（当前 18.7%）。

### 我明确不声称的

- 这是**相关，不是因果**。没有对照组，不能排除「复杂故障同时导致高积压和高失败」这种共同原因。
- 场景 B 的 +3,513h 是**上限估算**，假设积压能完全压到 <40h 水平，实际做不到。
- 华东总站的例外只说明「存在未观测到的保护因素」，**我没法从这份数据里指出是什么**。

### 敏感性：这个结论离临界点多近

主结论是贴着临界线的，这点必须自己说清楚，不能等被问：

| 检验 | 结果 | 含义 |
|---|---|---|
| 拦截成本临界值 | **14.00 小时** | 题干给 15h，只赢 1h。「拦截是亏的」是贴线结论，不是压倒性的 |
| 49 单未回传全算失败 | 整体 14.71% | 仍低于 20% 盈亏线，方向不变 |
| 高负荷阈值换 50 / 55 / 65 / 70h | 临界成本 10.23 / 11.92 / 12.63 / 14.50h | **五个阈值全部为亏**，结论不依赖阈值选在 60 |

`python repro.py --section 5`

**这也正是把主建议放在「降积压」而不是「拦截」上的原因**：降积压不依赖 15 小时这个参数。如果实际拦截成本低于 14 小时，拦截就会变成划算的——但这份数据里没有理由假设它不是 15。

## 5. 局限，以及如果还有时间

- **只有 6 天数据**，无法判断积压是否有周内规律（周末/月初高峰）。
- **`labor_hours` 是网点级快照**，同一时段同一网点的多张工单共享同一个值，因此不能当作工单级独立变量。分层复核已部分缓解，但严格推断需要工单级负荷。
- **没有技师维度**，无法区分「积压导致赶工」和「新手被派到高负荷时段」。
- 下一步第一件要做的事：**查华东总站做对了什么**（排班？技师配置？分级派工？），这比继续在数据里挖更有价值。
